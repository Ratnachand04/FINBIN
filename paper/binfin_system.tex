\begin{abstract}
We present BINFIN, an end-to-end system that ingests cryptocurrency price,
news, social and on-chain data, analyses it with a locally hosted quantised
large language model alongside a domain-specific transformer, forecasts
short-horizon price direction with a model ensemble, and emits explainable
trading signals -- entirely on a single commodity workstation with no
dependence on commercial model APIs. The system comprises $17{,}200$ lines of
Python across $169$ modules, $45$ HTTP and WebSocket endpoints, and eight
containerised services deployed by a single command. Three aspects of the design
are, we believe, of general interest beyond this application. First, a
\emph{hybrid split runtime} pins 4-bit NF4-quantised Mistral-7B inference to the
GPU while routing retrieval and parsing to CPU, and detects CUDA availability at
startup to fall back to CPU-only LoRA training when VRAM is unavailable, so the
same deployment runs on hardware ranging from an 8\,GB consumer GPU to a
CPU-only host. Second, a \emph{causality-by-construction} feature and execution
pipeline makes look-ahead structurally difficult rather than merely discouraged:
fills resolve only against bars at or before the signal, the feature scaler is
fitted on training folds and persisted as a model artefact, and train/test splits
carry an embargo sized to the longest feature window. Third, and most unusual for
a system of this class, BINFIN ships a \emph{verification harness} -- $29$
regression tests, a mutation-testing rig that reintroduces known faults and
confirms detection at a score of $8/8$, and a randomised null test asserting that
the backtester reports no edge on structureless data. We report both a systems
evaluation and, using that harness, an honest predictive evaluation. The latter
is negative: over $5{,}562$ out-of-sample daily predictions the ensemble attains
$52.95\%$ directional accuracy, statistically distinguishable from a coin flip
($p < 10^{-4}$) but not from inverse persistence at $52.88\%$, and its gross
annualised Sharpe of $0.544$ carries a bootstrap interval containing zero. We
argue that a platform able to establish that result reliably is more useful than
one that reports a large number it cannot defend, and we discuss what the
architecture would need in order to test richer hypotheses.
\end{abstract}

\section{Introduction}
\label{sec:intro}
%==============================================================================

Applied cryptocurrency research sits awkwardly between two kinds of
infrastructure. Institutional platforms are capable but proprietary, expensive
and unavailable for reproduction. Public research code is generally a single
notebook: a model, a train/test split and a printed accuracy, with no ingestion,
no serving, no execution simulation and no way to run it continuously. Between
these lies a gap that matters for anyone who wants to test a market hypothesis
end to end on their own hardware, on their own data, without sending that data to
a third party.

BINFIN was built to occupy that gap. It is a complete, self-hosted system: it
collects live price, news, social and on-chain data; scores unstructured text
with a locally hosted quantised large language model; forecasts short-horizon
direction with an ensemble of statistical and neural models; composes those
outputs into explainable buy/sell/hold signals; simulates their execution with a
cost- and latency-aware backtester; and serves the result over HTTP and
WebSockets to a live dashboard. It runs on one machine and requires no commercial
model API.

\subsection{Design goals}

Four constraints shaped the architecture, and each has visible consequences in
the design.

\paragraph{G1: hardware portability.} The system must run on a consumer GPU with
8\,GB of VRAM and must degrade to CPU-only rather than fail. This motivates 4-bit
NF4 quantisation of the language model, the split runtime of
Section~\ref{ssec:runtime}, and a startup capability probe that selects a
training path accordingly.

\paragraph{G2: data locality.} No market or user data may leave the host. This
rules out hosted LLM APIs and motivates the Ollama-based inference container and
the local FinBERT fallback.

\paragraph{G3: causality by construction.} Look-ahead bias should be structurally
difficult, not merely discouraged by convention. This motivates the bar-driven
execution loop, the fold-local scaler fitting, and the embargoed split of
Section~\ref{sec:causality}.

\paragraph{G4: verifiable claims.} Any number the system reports must be
defensible. This motivates the verification harness of
Section~\ref{sec:verification}, which we consider the least standard and most
transferable part of the work.

\subsection{Contributions}

\begin{enumerate}
    \item \textbf{A complete, deployable architecture} for multi-modal
    cryptocurrency signal generation on a single host, described in enough detail
    to reimplement (Section~\ref{sec:arch}): eight services, $45$ endpoints,
    $17{,}200$ lines of Python.

    \item \textbf{A hybrid split runtime} (Section~\ref{ssec:runtime}) that
    partitions a 7B-parameter language model workload between GPU and CPU by
    function rather than by layer, with automatic capability detection and a
    CPU-only LoRA training path.

    \item \textbf{A causality-by-construction pipeline}
    (Section~\ref{sec:causality}) covering feature computation, scaler
    lifecycle, split construction and execution semantics.

    \item \textbf{A verification harness} (Section~\ref{sec:verification})
    comprising regression tests, mutation testing and a randomised null test for
    the backtester, which we propose as a baseline standard for systems of this
    class.

    \item \textbf{An honest end-to-end evaluation} (Section~\ref{sec:eval}),
    including a negative predictive result that the harness makes trustworthy,
    and an analysis of which architectural choices the result implicates.
\end{enumerate}

\subsection{A note on what the evaluation shows}

We report in Section~\ref{ssec:predictive} that the system's forecasting layer,
as configured, does not outperform a zero-parameter baseline. We state this
plainly in the abstract and here rather than deferring it, because it shapes how
the rest should be read. The contribution claimed is the architecture and its
verification, not a profitable strategy. A platform whose measurements can be
trusted is a prerequisite for the second, and Section~\ref{ssec:caught}
enumerates several substantial errors the harness caught in the system's own
earlier revisions -- errors that, uncaught, would have produced a large and
entirely spurious reported Sharpe ratio.

\section{Related Work}
\label{sec:related}
%==============================================================================

\subsection{Cryptocurrency forecasting systems}

Most published cryptocurrency prediction work evaluates a model in isolation.
\citet{sezer2020financial} survey deep learning for financial time series and
observe wide inconsistency in evaluation protocol across the field.
\citet{fischer2018deep} and \citet{krauss2017deep} report on LSTM networks and
tree ensembles for equity direction with careful statistics but no deployed
system. \citet{mcnally2018predicting} apply recurrent networks to Bitcoin. Our
emphasis differs: the model families we use are deliberately standard, and the
contribution is the surrounding system and its verifiability.

\subsection{Financial text and domain language models}

\citet{tetlock2007giving} established that media sentiment carries information
about returns, and \citet{loughran2011liability} showed that general-purpose
lexicons misread financial language. FinBERT \citep{yang2020finbert}, built on
BERT \citep{devlin2019bert}, is the standard domain encoder and is the fallback
path in our sentiment subsystem. \citet{wu2023bloomberggpt} demonstrate the
capability of large proprietary financial models, which is precisely the
capability our design goal G2 forgoes in exchange for locality.

\subsection{Efficient adaptation and quantised inference}

LoRA \citep{hu2022lora} adapts large models through low-rank updates without
touching base weights, and QLoRA \citep{dettmers2023qlora} adds NF4
double-quantised backpropagation, making 7B-parameter fine-tuning feasible on a
single consumer GPU. These are the enabling technologies for G1, and our
contribution here is architectural rather than algorithmic: we show how to
partition such a workload in a running multi-service system with automatic
capability-based fallback.

\subsection{Correctness in financial machine learning}

\citet{lopezdeprado2018advances} formalises purging and embargoing and argues
that standard cross-validation is invalid for financial series.
\citet{bailey2014deflated} and \citet{harvey2016cross} address selection bias in
reported performance. \citet{arnott2019backtesting} propose a backtesting
protocol for machine learning. These works address statistical validity given a
correct engine. We complement them at the implementation layer, applying
mutation testing \citep{jia2011analysis} -- routine in software engineering,
rare in this domain -- to establish that a test suite actually detects the
faults it targets.

\subsection{Ingestion layer}
\label{ssec:ingest}

Four collectors run as supervised asyncio tasks under a Celery-backed worker
supervisor. Each implements rate limiting, bounded retry with exponential
backoff, and graceful degradation.

\begin{itemize}
\item \textbf{Price} (\texttt{price\_collector.py}) consumes the Binance
WebSocket stream for live ticks and REST klines for historical backfill. When
the socket drops, it fails over to an HTTP polling path rather than stalling the
pipeline -- a distinction that matters because a silently stalled price feed
produces stale features rather than an error.
\item \textbf{News} (\texttt{news\_collector.py}) polls NewsAPI plus three RSS
feeds (CoinTelegraph, CoinDesk, The Block), deduplicating by URL and title hash.
\item \textbf{Social} (\texttt{reddit\_collector.py}) uses PRAW against
cryptocurrency subreddits with its own token-bucket limiter and signal handlers
for clean shutdown.
\item \textbf{On-chain} (\texttt{data\_ingestion/}) crawls Etherscan with
adaptive block-range sizing to stay inside per-day call quotas, flagging
transfers above a value threshold as whale activity.
\end{itemize}

\subsection{Storage layer}

Persistence is PostgreSQL with the TimescaleDB extension. Five high-volume
tables are converted to hypertables with chunk intervals matched to write rate --
six hours for \texttt{price\_data}, one day for \texttt{sentiment\_scores},
\texttt{news\_data}, \texttt{reddit\_data} and \texttt{onchain\_transactions} --
with background retention policies. Fourteen tables in total cover market data,
derived sentiment, signals, predictions, backtest runs and trades, users and
per-user encrypted API keys.

Redis serves two roles: Celery broker, and a short-TTL cache for computed feature
vectors and predictions, keyed by symbol and timestamp.

\label{ssec:sentiment}

locally hosted generative model is powerful but fallible in output format and
availability.

The primary path sends a few-shot prompt to a Mistral-7B-instruct model
quantised to \texttt{q4\_K\_M}, served by Ollama in its own container. The prompt
constrains output to a JSON object carrying a sentiment label, a confidence and a
short reasoning string; the reasoning is retained and surfaced in the dashboard,
which is what makes signals explainable to the user rather than opaque. When the
model times out or emits unparseable output, the request falls through to
FinBERT running locally on CPU, which is deterministic and fast but produces no
rationale.

Per-symbol scores are aggregated into 24-hour and 7-day moving averages, a
velocity term (current minus 24-hour mean) and a dispersion term, and written to
a hypertable for downstream consumption.

\subsection{Forecasting subsystem}
\label{ssec:forecast}

Three model families are trained per asset and combined
(Figure~\ref{fig:forecast}):

\begin{itemize}
\item \textbf{Prophet} for additive trend and seasonality decomposition, with
exogenous regressors for sentiment and whale activity.
\item \textbf{LSTM} (Keras), a stacked recurrent classifier over $60$-step
windows of the feature matrix, with early stopping on validation loss.
\item \textbf{XGBoost} over the flattened window, retaining feature importances
for explanation.
\end{itemize}

Component probabilities are combined by a fixed weighting,
\begin{equation}
P_{\text{ens}}(c) = 0.30\,P_{\text{prophet}}(c) + 0.40\,P_{\text{lstm}}(c) + 0.30\,P_{\text{xgb}}(c),
\label{eq:ensemble}
\end{equation}
and an ensemble confidence is derived from the dispersion of component
predictions. We record explicitly that these weights are hand-set rather than
fitted; Section~\ref{sec:limitations} treats this as a limitation.

\subsection{Signal generation}
\label{ssec:signal}

The decision layer is deliberately rule-composed rather than learned, so that
every emitted signal carries a human-readable justification. A BUY requires all
three primary conditions, at least two of five supporting conditions, and zero of
four risk filters:
\begin{equation}
\textsc{buy} \iff
\underbrace{|\mathcal{P}| = 3}_{\text{primary}} \;\wedge\;
\underbrace{|\mathcal{S}| \ge 2}_{\text{supporting}} \;\wedge\;
\underbrace{|\mathcal{R}| = 0}_{\text{risk}} ,
\label{eq:signal}
\end{equation}
with the sets as given in Table~\ref{tab:signal}. SELL is the mirror. Anything
else is HOLD. A cooldown and duplicate check suppresses repeated signals on the
same symbol within a window.

Price targets and stops are placed from ATR and scaled by a user-supplied risk
appetite, and a reward-to-risk ratio is reported alongside each signal.

\subsection{Execution simulation}
\label{ssec:backtest}

The backtester is bar-driven rather than signal-driven. It iterates the union of
bar timestamps; at each timestamp it resolves exits for open positions using
\emph{that position's own} asset bar, then opens positions scheduled for that
bar, then closes positions whose bar-counted holding period has expired.

Three semantics are worth stating because they are the usual sources of
overstated backtest performance:
\begin{enumerate}
\item A signal computed from the close of bar $i$ is scheduled for bar $i+1$ and
filled at its open, so no fill can reference information at or after its own
execution bar.
\item Stops and targets are evaluated against each bar's high and low, not the
close; when a single bar touches both levels the stop is assumed to fill, the
pessimistic convention.
\item Equity carries shorts as a liability,
$V_t = \text{cash}_t + \sum_{\text{long}} q_j p_t^{(j)} - \sum_{\text{short}} q_j p_t^{(j)}$,
and each leg is charged fees on its own notional.
\end{enumerate}

Token generation, the VRAM-hungry and latency-critical operation, runs in the

lookup, database routing, prompt construction -- is pinned to CPU by
configuration (\texttt{RAG\_CONTEXT\_CPU\_ONLY}), because it is memory-bandwidth
rather than compute bound and would otherwise consume VRAM that the model needs.

\subsection{Serving, workers and observability}

The API is FastAPI with $45$ endpoints spanning market data, sentiment,
predictions, signals, backtests, model operations, authentication and
per-user API key management, plus three WebSocket channels
(\texttt{/ws/live-data}, \texttt{/ws/market}, \texttt{/ws/notifications}) that
push tick updates and signal notifications to the dashboard.

Long-running work is offloaded to Celery: ingestion supervision, scheduled signal
generation, backtest execution, and fine-tuning jobs with a 24-hour task limit
and cancellation support. Prometheus counters instrument ingestion restarts and
per-task errors, scraped into Grafana dashboards provisioned as code.

The whole stack -- TimescaleDB, Redis, Ollama, backend, frontend, Prometheus,
Grafana, LLM trainer -- is eight Compose services brought up by one command, with
a GPU overlay file for CUDA-enabled hosts.

\section{Causality by Construction}
\label{sec:causality}
%==============================================================================

Design goal G3 asks that look-ahead be structurally difficult. Four mechanisms
implement it.

\paragraph{Causal features.} Every feature is a function of bars indexed $\le t$.
Rolling statistics use trailing windows only; window normalisation is computed
per lookback window rather than globally, so no statistic is informed by data
after the observation it describes.

\paragraph{Scaler lifecycle.} The feature scaler is fitted on training rows only,
persisted alongside the model artefacts, and loaded at inference where it is
applied through \texttt{transform} rather than \texttt{fit\_transform}. This
separation is enforced by the API surface: the serving path has no method that
fits. If no fitted scaler is present the system logs a warning and returns
unscaled features rather than silently producing a degenerate vector.

\paragraph{Embargoed splits.} Because training samples are $60$-step windows with
next-bar labels, and some features use windows up to $672$ bars, adjacent samples
overlap in time. Splits therefore discard a gap
\begin{equation}
\mathcal{T}_{\text{train}} = [0, k), \quad
\mathcal{T}_{\text{test}} = [k + e, n), \quad e \ge L_{\text{seq}} + h,
\label{eq:embargo}
\end{equation}
following \citet{lopezdeprado2018advances}.

\paragraph{Execution semantics.} As described in Section~\ref{ssec:backtest},
bar lookup is constrained to $\{i : t_i \le t_{\text{signal}}\}$ by binary
search, making it structurally impossible for a fill to resolve against a future
bar.

\section{Verification Harness}
\label{sec:verification}
%==============================================================================

Design goal G4 asks that reported numbers be defensible. Systems of this class
almost never ship the means to check that. BINFIN ships three.

\subsection{Regression suite}

Twenty-nine tests use hand-built fixtures with analytically known answers rather
than database data, so they run without infrastructure. They cover no-look-ahead
fills, per-asset position pricing, short accounting, intrabar exit resolution,
holding-period semantics, Sharpe annualisation against its closed form, bootstrap
non-degeneracy, scaler behaviour and split disjointness.

The strongest is a closed-loop accounting invariant: with all positions flat at
the end of a run,
\begin{equation}
V_T - V_0 = \sum_{i=1}^{N} \mathrm{PnL}_i
\label{eq:reconcile}
\end{equation}
must hold exactly. Any fault that creates or destroys cash violates it, and it
cannot be satisfied by accident.

\subsection{Mutation testing}
\label{ssec:mutation}

A test count measures effort, not coverage. To establish that the suite detects
what it targets, a pytest plugin reintroduces one known fault before collection,
selected by environment variable, and a driver runs the suite once per fault.

\subsection{Randomised null test}
\label{ssec:null}

Random entry signals on a driftless geometric random walk contain no structure by
construction, so a correct engine charging positive costs must lose at a rate set
by turnover and cost alone.

The assertion must be distributional. A $75$-day fixture has
$\mathrm{SE}(S) \approx 2.2$, so asserting $S \le 0$ on a single path fails on a
correct engine a substantial fraction of the time -- measured here, $13.3\%$ of
seeds produce a positive Sharpe, with a range of $-10.45$ to $+7.33$. Running
$60$ independent seeds gives $\bar{S} = -3.534$, $\mathrm{se} = 0.470$,
$t = -7.51$, alongside cash conservation to $1.2 \times 10^{-11}$ on runs ending
flat and a fee-rate check against the modelled two-sided fee.

\paragraph{Coverage, stated honestly.} This exercises the \emph{engine} with
exogenous signals. It is blind to feature leakage, split leakage and imputation
leakage, which live upstream. It is one necessary check among several, not a
sufficient one.

Read against inverse persistence, it does not. Paired comparisons on identical
days give differences of $-0.29$, $+0.53$ and $-0.07$ percentage points on BTC,

reversal effect, and the feature engineering, ensemble and training machinery add
nothing measurable on top of it.

\emph{below} the unweighted accuracy on every asset ($51.68$, $51.57$, $52.33$

Sharpe of $+0.113$ ungated to $-0.309$ at $|p - 0.5| \ge 0.08$ -- the ensemble
confidence of Section~\ref{ssec:forecast} is not merely uninformative but mildly
anti-informative.

\subsection{What the harness caught}
\label{ssec:caught}

The verification layer is the component we would most defend, because it changed
the system's own reported numbers by more than their magnitude. Before the
harness existed, this system reported an aggregate annualised Sharpe of $4.54$
with a per-series maximum of $23.65$. Those figures were artefacts of twelve
code-level faults, including:

\begin{itemize}
\item exits priced from the wrong asset's bar in multi-asset runs;
\item a bar lookup selecting the nearest bar by absolute time distance, which
could resolve into the future;
\item Sharpe computed by annualising per-trade returns with a fixed
$\sqrt{252}$, the single largest contributor to the $23.65$;
\item shorts marked to market with the wrong sign, so a short gained equity as
price rose;
\item a Monte Carlo routine that shuffled a P\&L vector and summed it, which is
permutation-invariant and therefore constant across all simulations;
\item a feature scaler fitted on a single row at inference, which returns
identically zero, so every served prediction ran on a zero vector.
\end{itemize}

Several survived long review because they \emph{compensate}: the inverted short
accounting corrupted the equity curve, but Sharpe was computed from the trade
record and never touched it. This is the argument for testing the instrument
directly rather than inspecting outputs for plausibility, and it is why we regard
the harness as part of the architecture rather than an accessory to it.

\section{Discussion}
\label{sec:discussion}
%==============================================================================

\subsection{What the negative result implicates, and what it does not}

The result in Section~\ref{ssec:predictive} is a statement about a specific
configuration: thirty-four single-asset technical features, a fixed-weight
ensemble, a daily horizon and retail taker costs. It is not a statement about the
architecture. The ingestion, storage, serving and verification layers are
agnostic to what is predicted; the finding indicts the feature set and the
decision layer, both of which are replaceable within the same system.

Concretely, three design choices are implicated. The ensemble weights of
\eqref{eq:ensemble} are fixed rather than fitted. The feature set omits every
crypto-specific microstructure signal -- perpetual funding, open interest, basis,
liquidation cascades, order-book imbalance, exchange netflows, cross-asset
lead--lag. And the training objective is log-loss on direction, when the binding
constraint turns out to be transaction cost, which belongs in the loss.

\subsection{The value of a system that can produce a negative result}

Most systems in this class cannot establish a negative result, because their
measurement layer would not survive the attempt. We think that is the more
important observation. The same harness that produced $52.95\%$ would have
produced $4.54$ Sharpe eighteen months earlier and been believed. The difference
is not the model; it is that the instrument is now calibrated, and the
calibration is shipped so that a reader can re-run it.

\subsection{Explainability as an architectural property}

Two decisions make signals inspectable rather than opaque. The generative
sentiment path returns a reasoning string that is stored and surfaced alongside
the score. And the decision layer is rule-composed
(Equation~\ref{eq:signal}), so every signal carries the specific conditions that
fired. This costs predictive flexibility -- a learned decision layer would
plausibly do better -- and it is a deliberate trade for a system intended to be
audited by its operator.

%==============================================================================
\section{Limitations}
\label{sec:limitations}
%==============================================================================

\paragraph{Fixed ensemble weights.} Equation~\eqref{eq:ensemble} uses hand-set
weights. They were never fitted, and no ablation establishes that three model
families outperform one.

\paragraph{Feature scope.} Single-asset OHLCV and derived technicals only. The
negative predictive result should be read as scoped to this feature set.

\paragraph{Synthetic sentiment in the training corpus.} The historical sentiment
series shipped for offline experimentation is generated from same-day returns
rather than real text, and correlates $0.916$ with the contemporaneous return and
$-0.018$ with the next day's. It is excluded from all reported results, and no
claim in this paper concerns sentiment-driven prediction. Validating the live
sentiment path against real labelled financial text remains outstanding.

\paragraph{No latency or throughput benchmarks.} We report the deployed topology
and resource floor but not measured end-to-end inference latency, ingestion
throughput or GPU memory profiles under load. For a systems paper this is a
genuine gap and is the first item of further work.

\paragraph{Cost model.} A flat $4$\,bps taker plus $5$\,bps slippage per side is
likely conservative for BTC and ETH at daily horizon, where passive execution is
feasible. A defensible passive assumption would move the point estimate above
breakeven, though not outside the confidence interval.

\paragraph{Instrument idealisation.} We model Binance spot but evaluate a
long/short book, which requires margin. Funding, borrow availability and
liquidation are not modelled.

\paragraph{Mutation coverage.} Eight of thirteen expressible faults are covered
by the mutation rig; five are covered only by direct tests.

\paragraph{Single-node.} No horizontal scaling, no multi-tenant isolation, no
capacity analysis, and no live or paper-trading validation.

%==============================================================================
\section{Conclusion}
\label{sec:conclusion}
%==============================================================================

We described BINFIN, a self-hosted system that ingests multi-modal
cryptocurrency data, analyses text with a locally hosted 4-bit quantised
Mistral-7B alongside FinBERT, forecasts direction with a model ensemble, composes
explainable signals, simulates their execution, and serves the result --
$17{,}200$ lines of Python, $45$ endpoints, eight containers, one command to
deploy, on hardware as modest as a $16$\,GB workstation with no discrete GPU.

Three elements are transferable beyond this application: a hybrid split runtime
that partitions a large-model workload by function and degrades by capability
rather than failing; a causality-by-construction pipeline that makes look-ahead
structurally difficult across features, scaler lifecycle, splits and execution;
and a verification harness -- regression tests, a mutation score of $8/8$, and a
randomised null test -- that we propose as a baseline standard for systems of
this class.

Evaluated with that harness, the forecasting layer attains $52.95\%$ directional
accuracy over $5{,}562$ out-of-sample predictions, which is distinguishable from
a coin flip but not from a zero-parameter baseline, and its gross Sharpe interval
contains zero. We report this rather than the $4.54$ Sharpe the same system
produced before the harness existed. The architecture is what we offer; the
negative result is what it lets us establish honestly, and we regard the second
as evidence for the first.
